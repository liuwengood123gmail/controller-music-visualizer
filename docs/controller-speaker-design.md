# 手柄扬声器同步播放 · 设计文档

> 状态：待实现。写给接手的开发者 / agent。目标：Mac 正在播放的声音，**同时**从 DualSense 的内置扬声器放出来（Mac 音响照常播放、不受影响），并与震动协调。
> 先读 README「设计思路」和 [multi-controller-design.md](multi-controller-design.md)；代码在 `Sources/ControllerMusicVisualizer/`。

## 1. 已确定的需求

| # | 需求 |
|---|---|
| R1 | 只用手柄**内置扬声器**（不处理耳机孔） |
| R2 | Mac 当前的输出设备（音响）照常播放，手柄扬声器**额外**同步播放；**不能改动或静音系统输出** |
| R3 | 每个手柄独立设置：开关「手柄扬声器同步播放」（默认关）+ 音量（默认 **30%**） |
| R4 | 只有 **USB** 连接的 DualSense 显示这两项（蓝牙不支持，见 §7） |
| R5 | 试听和默认值都要**轻**，不能吵 |
| R6 | 实现者在云端拿不到手柄：**先自行把延迟、协调性调到理论最优**，并把可调参数暴露出来，交给仓库作者在本机微调（§5、§6） |

## 2. 硬件与协议（已实测）

**USB 音频设备**：DualSense 在 USB 下是 4 声道输出设备，第 1/2 声道 → 耳机孔 / 扬声器，第 3/4 声道 → 左/右震动单元（HD 震动已在用）。设备匹配方式见多手柄文档 §6（UID 后缀 `:<locationID hex>:1`）。

**扬声器默认是关的**：macOS 在「声音」里选 DualSense 作为输出也没有声音。必须先发 HID 输出报告打开扬声器通路（PS5 和 Linux 都会主动发，macOS 不会）。

**报告字段**（参考 Linux `drivers/hid/hid-playstation.c`，与本项目 `DualSenseReport` 的 47 字节 common 结构一致）：

| common 偏移 | 字段 | 生效标志位 |
|---|---|---|
| 5 | `speaker_volume` | flag0 bit5 |
| 7 | `audio_control`：bit4–5 = 输出路径 | flag0 bit7 |
| 37 | `audio_control2`：bit0–2 = 扬声器前置放大 | flag1 bit7 |

输出路径（Linux 注释）：

```
0  耳机 L-R，扬声器静音
1  耳机 L-L，扬声器静音
2  耳机 L-L，扬声器 ← R
3  耳机静音，扬声器 ← R      ← 本功能用这个
```

扬声器只接收**右声道**（第 2 声道）。Linux 注释：扬声器音量有效范围约 **0x3d–0x64**；Linux 打开扬声器时设音量 0x64、前置放大 2（+6dB）。

**本机实测**（USB，测试音 440Hz、幅度 0.15，路径 3）：

| 组 | 音量 | 前置放大 | 结果 |
|---|---|---|---|
| 1 | 61 (0x3d) | 0 | 听不到 |
| 2 | 73 | 0 | 能听到 |
| 3 | 73 | 2（+6dB） | 能听到，与 2 差不多 |
| — | 30 | — | 听不到（低于有效范围，等于静音） |

结论：**硬件音量可用范围窄、档位粗**，不要用它做音量滑块。

> 发送音频字段时，flag0 要保留 bit1（兼容震动模式位）的现有语义，不能误清 bit0/bit1——它们兼有震动模式切换作用（HD 模式下两位都清零）。音频字段应合并进现有的 `DualSenseReport.make`，由 `DualSenseOutputState` 增加 `speaker`（开 / 关 / 交出时恢复）状态，不要另发一路报告与现有的 0.1 秒定期重发互相覆盖。

## 3. 方案

App 已经用 `SystemAudioTap` 采集整机声音（排除了本进程）。把这份声音再复制一份，写进手柄的第 1/2 声道：

```
SystemAudioTap ─► MusicAnalyzer（现有）
      │
      └─► SpeakerFeed（新，共享）：单声道混合 → 高通 → 限幅 → 环形缓冲（48kHz）
                                                         │
ControllerSession（USB DualSense）── DualSenseAudioOutput（由 HDHapticOutput 扩展）
                                       ch1/2 ◄── SpeakerFeed（× 软件音量）
                                       ch3/4 ◄── HD 震动（现有）
```

- **`DualSenseAudioOutput`**：把现在的 `HDHapticOutput` 扩展为「手柄音频输出」，第 1/2 声道放扬声器声音，第 3/4 声道放 HD 震动。两者可独立开关（只开扬声器、不开 HD 也要能用）。共享同一个 AUHAL，天然同一时钟、同一延迟。
- **`SpeakerFeed`**：与 `HapticWaveform` 同样的单写单读环形缓冲 + 跨设备时钟的读位置追赶逻辑；所有手柄共享一份，每个输出有自己的读位置。
- **HID**：开关打开 → 路径 3、硬件音量固定（建议 0x64，前置放大 0；见 §5 可调）；关闭 / 停止 / 交出 → 发一次路径 0 再放手（与现有「交出控制权先发默认值」一致）。
- **系统声音采集的启动条件**（`AppModel`）：现在只在「跟随音乐 + 震动或灯光由 App 控制」时采集；改为「或任一启用的手柄打开了扬声器同步」。按摩模式下扬声器也应能同步播放。
- **不会回声**：tap 排除了本进程，手柄放出的声音不会被再次采集。

## 4. 声音处理（`SpeakerFeed`，纯函数部分要能单元测试）

1. **单声道**：`(L + R) / 2`，同时写入第 1、2 声道（扬声器取第 2 声道）。
2. **高通**约 200Hz（二阶）：小扬声器放不出低频，硬放会破音、嗡嗡响，并通过外壳传成震动，和马达混在一起。
3. **音量**：软件增益，滑块 0–100% 按对数（分贝）曲线映射，0% = 完全静音（此时可以不打开扬声器通路）。**默认 30%**。
4. **限幅**：软限幅（如 tanh 或带 1–5ms 起始的峰值限幅器），防止爆音。
5. 开 / 关 / 换手柄时 10–20ms 淡入淡出，避免咔哒声。

## 5. 延迟与协调性：先在代码里调到最优

**目标**：手柄扬声器尽量贴近 Mac 音响；扬声器与震动同时到达。

### 5.1 延迟从哪里来（实现者应逐项计算并记录）

```
Mac 音响听到的时刻 ≈ 应用写入 + 输出设备延迟（Mac 输出设备）
手柄扬声器听到的时刻 ≈ 应用写入
                      + tap 聚合设备 IO 周期（输入缓冲）
                      + SpeakerFeed 环形缓冲目标余量
                      + DualSense 输出 IO 周期（缓冲帧数）
                      + DualSense 设备延迟 + 安全偏移（kAudioDevicePropertyLatency / SafetyOffset / 流延迟）
```

- 用 `kAudioDevicePropertyBufferFrameSize`、`kAudioDevicePropertyLatency`、`kAudioDevicePropertySafetyOffset`、`kAudioStreamPropertyLatency` 读出两边的数值，**计算手柄相对 Mac 音响的额外延迟**，在调试信息里显示（例如窗口底部一行小字或日志）。
- **能压的都压**：
  - DualSense 输出的 IO 缓冲帧数尽量小（尝试 128 / 256 帧，按 `kAudioDevicePropertyBufferFrameSizeRange` 取允许的最小稳定值）；只设本 App 打开的 AUHAL 实例，不改系统默认输出设备。
  - 聚合设备（tap）的 IO 缓冲同样尽量小。
  - 环形缓冲目标余量从现在 HD 用的 20ms 往下试（例如 8–15ms），以「不欠载」为底线：统计欠载 / 追赶次数，自动在一个范围内选最小的稳定值。
- **无法做到零**：手柄必然比 Mac 音响晚（R2 不允许延迟 Mac 音响）。只需要压到人耳不明显（目标 < 20–30ms）。

### 5.2 与震动的协调

- **HD 震动**（USB）和扬声器在同一个 AUHAL、同一缓冲 → 天然对齐，确认两路读的是同一时刻的数据即可（`HapticWaveform` 与 `SpeakerFeed` 的读位置应同步推进，或合并为同一个缓冲的两个通道）。
- **兼容震动**（HD 关闭时，经 HID 报告，每 10ms tick）路径比音频快或慢都有可能：估算两者延迟差，必要时给较快的一路加一个固定延迟让它们对齐，并把这个延迟做成可调参数。
- 跟随音乐时，**震动的鼓点应和扬声器里听到的鼓点同时**。可以写一个离线测试：合成一段底鼓脉冲，分别经过「扬声器链路」和「震动链路」的处理代码，测量两路输出峰值的时间差（只算软件部分），作为对齐的基线。

### 5.3 可调参数（交给本机微调，不需要重新编译）

用 `UserDefaults`（`defaults write com.liuliu.ControllerMusicVisualizer <key> <value>`）暴露，启动时读取，未设置时用代码里调好的默认值；README 的「其他」里列出：

| 键 | 含义 | 建议默认 |
|---|---|---|
| `speaker.hwVolume` | 扬声器硬件音量（0x3d–0x64） | 0x64 |
| `speaker.preamp` | 前置放大 0–7 | 0 |
| `speaker.highpassHz` | 高通截止频率 | 200 |
| `speaker.bufferMs` | 环形缓冲目标余量 | 实现者调出的最小稳定值 |
| `speaker.ioFrames` | DualSense 输出 IO 缓冲帧数 | 实现者调出的最小稳定值 |
| `speaker.hapticsDelayMs` | 兼容震动相对扬声器的对齐延迟（可正可负） | 由估算得出 |

## 6. 云端开发、本地测试的分工

- 单元测试（`swift test`，CI 已有）：单声道混合、高通频响（50Hz 明显衰减、1kHz 基本不变）、软件音量曲线（0% 静音、30% 默认、100% 不削波）、限幅、淡入淡出、环形缓冲欠载与追赶、HID 报告里的扬声器字段与标志位（开 / 关 / 交出，且不影响震动模式位）、延迟估算函数（喂设备属性数值，检查算出的总延迟）、§5.2 的离线对齐测试。
- PR 描述里给出：估算出的延迟分解、选定的缓冲参数及理由、需要本机确认的清单（§8）。

## 7. 不做 / 限制

- **蓝牙**：蓝牙下声音走索尼私有的压缩打包报告；之前蓝牙 HD 震动实验中 macOS 发送速率只有所需的约 1/3，扬声器更不可行。蓝牙时隐藏这两项。
- **耳机孔**：本次不做（R1）。插着耳机时 Linux 会把扬声器静音、改走耳机；本功能保持路径 3 即可。
- 音质有限：适合游戏音效、人声；不追求音乐音质。

## 9. 现有代码中的经验与陷阱（务必遵守）

- 系统录音权限弹窗会阻塞 Core Audio 调用：采集在后台线程启动（现有 `startTap()`）。
- App 创建 / 销毁聚合设备会触发设备列表变化通知：只有连接方式真的变化才重启会话。
- HID 共享管理器已挂主线程事件循环并在使用前显式打开设备（之前两次 bug：换口重插打不开、运行中插入枚举不到）。
- 震动标志位兼有模式切换作用：bit0/bit1 都清零 = HD 模式；交给游戏时只置 bit1。
- 交出控制权时先发一次默认值，否则手柄保留旧设置。
- 不要在属性观察器里用 `inout` 传自身属性再调用会修改它的方法（Swift 独占访问冲突，曾导致闪退）。
- 实时音频线程里不要加锁、分配内存或调用 Objective-C / Swift 运行时重的东西；沿用现有渲染回调的写法。
